# Exploration: mvp-dynamic-roles-jobs

## Current State
Trust Work Escrow runs Dioxus 0.7 + Axum (backend/api via MetadataRepository) + Solana Anchor (trust-escrow-v3, devnet 7a2Y...). Verified today:

- `app/src/route.rs`: Two layout groups: `MarketingLayout` (`/`, `/login`, `/signup`, `/contact`, `/docs`) and `DashboardLayout` (`/dashboard/client`, `/freelancer`, `/admin`, `/config` + arbitration routes). No Jobs hierarchy exists.
- `app/src/ui/dashboard_layout.rs` + `app/src/ui/sidebar.rs`: Single `Sidebar(role: DashboardRole)` instance. `DashboardRole::{Client,Freelancer,Arbiter,Admin}` derived from `auth.user.read().role` global. Static links per role (Client→Mis Jobs, Freelancer→Jobs disponibles, shared Config·Wallet). Header shows `email` + short pubkey + guest badge.
- `app/src/features/dashboard/mod.rs`: Two separate pages `ClientDashboard` (creates jobs via `request_create_job_transaction` + `relay_signed_job_transaction` signed by Phantom) and `FreelancerDashboard` (read-only listing + mock `apply_msg`). Both gate with `can_act = !is_guest && wallet.is_some()` and role hints (`is_client_role`, `is_freelancer_role`). No distinction per job.
- `app/src/server/auth/guest.rs`: `User { email, wallet_pubkey: Option<String>, role: String, is_guest }` — single wallet, global role string. Hydrated via `get_me()` (guest default) + JWT `twe-jwt`.
- `app/src/server/auth/users.rs` + `app/src/server/auth/api_client.rs` + `backend/api/src/routes.rs` + `backend/api/src/metadata.rs` + `backend/api/src/repository.rs`: Persistence lives in `backend/api` ( `MetadataRepository` — in-memory for tests, Postgres/Mongo pending). `UserMetadata { email PK, role: String, wallet_pubkey: Option<String>, is_guest, created_at, updated_at }` validates `role ∈ {client,freelancer,admin,arbiter,guest}` and wallet as 32-byte bs58. Routes: `POST /users/login-or-create` (idempotent upsert, keeps wallet), `GET /users/:email`, `POST|DELETE /users/:email/wallet`. No multi-wallet, no per-job role.
- `backend/api/src/models.rs` + `backend/sdk/src/types.rs`: `JobMetadata { pda_address, title, description, amount, fee_amount, status: JobStatus, deadline }` + `JobResponse { job_id, client, freelancer, amount, status, job_pda, applicants_count }`. Applications are separate `ApplicationMetadata` (`application_pda` derived from job_id+index+applicant suffix) and on-chain `Application` PDA. No participant-role collection per job beyond `client` vs `applicant`.
- `app/src/features/dashboard/config.rs` + `app/src/solana/phantom.rs` + `app/src/server/auth/siws.rs`: ConfigPage handles single Phantom connect/disconnect via SIWS (`request_siws_challenge` / `verify_siws_server`, `sign_message`). Keys never leave browser. `link_wallet_persist` / `unlink_wallet_persist` delegate to backend/api.

Stack constraint respected: Dioxus 0.7, Axum, Anchor 0.32 / Rust 1.89, Postgres/Mongo via `MetadataRepository` trait.

### Approaches
1. **Global Role (status quo + toggle)**
   - Keep `User.role` as single source. Add UI toggle Client↔Freelancer.
   - Pros: Minimal code; no DB migration; sidebar logic already exists; easy JWT.
   - Cons: Fails core requirement (same user cannot be client on job A and freelancer on job B without switching global state; race conditions if they publish and apply concurrently). Forces alt-account workaround the user explicitly rejected. History/Balance per-role becomes ambiguous.
   - Effort: Low

2. **Pure Per-Job Role (proposed, off-chain JobParticipants)**
   - Remove `User.role` as authz source (keep as deprecated display preference). Introduce `job_participants` (or `JobParticipantMetadata`) with `{job_pda, user_email, wallet_pubkey, role_per_job: client|freelancer, joined_at}` and `user_wallets {email, pubkey, purpose: publish|apply, label}`. Creator = client participant, applicant accepted = freelancer participant. Applications still exist; acceptance promotes to participant. `Sidebar` becomes single `Jobs` tree, filtering pages by `participant.role`. `GET /jobs?role=published|accepted|history&email=...` derives from participants. Authz per endpoint checks participant role, not global role. Multi-wallet: publish-wallet used for `create_job` SIWS, apply-wallet for `apply_to_job`; Config→Conectar varias wallets manages them; optional on-device keypair generation (Solana `Keypair::new()` + export encrypted).
   - Pros: Matches requirement exactly (dynamic per job, same account both sides). Clean separation: on-chain `Job.client` immutable, off-chain role truth until on-chain freelancer assignment. Enables correct History (published+realized combined with filters), Disputas/Chat scoped to job participants, Balance split `gastado vs ganado`. Scales to múltiples wallets without altering program. Sidebar simplification (one menu).
   - Cons: Largest surface: ~12 files + 2 new tables/collections + API aggregation + UI redesign. Must migrate existing users (single wallet → `publish` wallet). Sidebar luxury polish requires new component library for expandable submenus. Balance comparativo needs aggregation not in `MetadataRepository` yet.
   - Effort: Medium-High

3. **Hybrid Global Preference + Per-Job Override (`JobParticipants` with fallback)**
   - Keep `User.role` as default preference (used for navbar badge, initial menu highlight), but authorize strictly via `JobParticipants` if entry exists, fallback to global. Same DB as Approach B but leaves `users.role` writable via `login-or-create` (admin/arbiter still global roles). Sidebar renders `Jobs` unified but can still expose quick switch for preference. Migration is additive: existing rows get `role` fallback, new writes populate participants. Wallets hybrid too: `wallet_pubkey` legacy alias → `publish` wallet, new `apply` wallet added via `connect extra wallet`.
   - Pros: Backward compatible (no breaking change for current `login_or-create` clients, tests, or governor). Arbiter/Admin remain global (correct, they are not per-job). Allows gradual rollout: Phase 1 keep global for config/admin, per-job for jobs. Lower risk of orphaned users. Easiest rollback.
   - Cons: Conceptual complexity (two sources of truth; must document precedence). Slightly more code paths (fallback checks). Global role can confuse if user expects pure per-job — mitigated by hiding global toggle in Jobs pages.
   - Effort: Medium (same DB as B, but less disruptive to auth)

### Recommendation
Adopt **Approach 3 — Hybrid with Per-Job Authority** as implementation path that converges to **Approach 2** semantically.

Rationale: The user explicitly said "rol dinámico por job, no rol global fijo" — global role must cease to gate job actions. Hybrid satisfies this with minimal breakage: keep `User.role` for `admin`/`arbiter`/`guest` (legitimately global) and for backward compatibility, but make `JobParticipants` the authoritative source for `client`/`freelancer` on every job endpoint. Start with additive migrations (`user_wallets`, `job_participants`) without dropping `users.role` or `users.wallet_pubkey`. Frontend removes `DashboardRole` branching immediately and ships the luxury `Jobs` sidebar (expandable, icons, dcdev #120808 footer, theme-aware). Creator wallet → `purpose=publish`, applicant wallet → `purpose=apply`; Config subitems separate them and optionally generate a Solana keypair (store encrypted, show pubkey, allow Phantom import).

This gives MVP the exact capability: same email publishes Job #7 (client via publish wallet) and applies to Job #9 (freelancer via apply wallet), with Published / Accepted / Historial correctly partitioned, chat/evidencias/disputas scoped per participant, and Balance comparativo `gastado (como client) vs ganado (como freelancer)` computed off-chain.

### Risks
- **On-chain authority leak**: `Job.client` is immutable on-chain; if `job_participants` diverges (e.g., DB says freelancer is X but on-chain `freelancer` not yet set), privileged actions (`accept_application`, `approve_work`, `release`) may fail on-chain check. Mitigation: treat on-chain as final for payouts, API as UX gate; enforce `client pubkey == job.client` on create/accept.
- **Self-apply & duplicate apply**: Same wallet publishing and applying to own job must be blocked API-side (`apply_to_job` returns 400 if `applicant == job.client` or participant already exists). Need dedup on `application_pda` (job_id+index+applicant truncation handled by `application_pda` helper).
- **Multi-wallet SIWS confusion**: Two wallets → two SIWS challenges; `x-pubkey` must match signing wallet's purpose or backend rejects. UX must clearly label "Firms con wallet de publicación" vs "Firms con wallet de solicitud". Store `purpose` in JWT to prevent swap.
- **Keypair generation responsibility**: "Crear en Solana + ver keypair" implies generating `Keypair::new()` server or client-side. Client-side only; never persist secret in `backend/api` plaintext. If shown, require password-encrypted export (e.g., `bs58 + warn once`). Otherwise delegate to Phantom entirely.
- **History filters friendliness**: Combined published+realized Historial with filtros amigables + read-only detail + chat/evidencias/disputas-if-any requires aggregating across `jobs`, `applications`, `milestones`, `disputes`, `evidence`. In-memory repo has no indices; Postgres needs `GIN`/composite index on `(job_pda, participant_email)`. Design filters as enum `Filter { All, Published, Accepted, Disputed, Completed }` mapped to `JobStatus` + participant role.
- **Disputas split**: User wants `Disputas → Abiertas / Historial` as top-level. Currently disputes are per-job (`dispute_pda` per job). Need `GET /disputes?scope=open|history&email=...` joining `disputes` + `job_participants`. Avoid duplicating `support_ticket` semantics.
- **Balance comparativo**: No ledger yet — `Saldo` filters `publicados vs realizados + comparativo gastado vs ganado` must be derived from `JobMetadata.amount + status ∈ {Submitted, Approved, Released}`. Without settlement receipts, numbers are mock; document as off-chain estimate until on-chain payout events are synced via `sync` module.
- **Sidebar luxury & mobile**: Unified Jobs menu with 6 top entries + 12 subitems risks overflow on 1024px. Requires collapsible groups (accordion), icons, persistence in `localStorage` (theme/font/size already in Configurar app), and a11y keyboard nav.
- **Stack & commit hygiene**: Must keep `dcdev/i18n`, `theme::Mode`, `Dioxus 0.7` patterns, `MetadataRepository` trait, Anchor 0.32, and commit-per-change. No direct Postgres in `app` (via `backend/api` only). No wallet secret in server logs (`redact_for_log` already in routes).
- **400-line PR guard**: Unified Jobs sidebar + 8 new pages + 2 migrations easily exceeds review budget. Forecast high → chain PRs.

### Ready for Proposal
Yes. Scope is bounded (single change, additive migrations, no contract rewrite for MVP). Next step is `sdd-propose` with: Intent (per-job dynamic roles + Jobs menu luxury), Scope (route/sidebar/dashboard/config/backend DB/UI), Approach (hybrid JobParticipants + multi-wallet), rollback plan (keep legacy `users.role`/`wallet_pubkey` alias), and delivery strategy `ask-on-risk` with chained PR forecast.
